## 状态补记（2026-05-08）

当前实现状态需要和原始规划版区分看待：

- `M1-M3` 的核心业务闭环已基本打通，系统已经具备“导入/场景生成/排程/Gantt/diff/版本治理基础”的 UAT 演示能力。
- 其中已落地的核心能力包括：`Resource / Recipe / Demand / Downtime / InventoryBalance / SetupRule` 导入、错误报告、场景生成、`Demand + Recipe -> Operation/Task` 展开、`precedence / setupRules / materialInputs / materialOutputs / inventoryBalances` 下传 solver、版本 diff / history / ready-for-release / publish / rollback / trial solve。
- 当前仍不建议表述为“二期所有规划项全部完成”。主要未收口项集中在 `M4` 和 `M5` 的产品化尾项：Redis-backed queue、`QUEUED / TIMEOUT / CANCELLED` 完整状态机、取消/重试、正式 `approve / reject` 审批流、后端角色权限、完整 actor attribution。
- 对外口径建议统一为：`二期核心能力完成，可进入业务演示/UAT；二期产品化收尾未全部完成。`

## 2. 项目背景

当前 APSPOC 已具备一条可运行的 POC baseline：

- 前端工作台：登录、会话、双语、版本列表、Gantt、导入导出、版本治理入口。
- 后端服务：Spring Boot 编排、异步排程任务、PostgreSQL 持久化、版本/Gantt API、审计事件。
- 求解器：FastAPI + OR-Tools CP-SAT，支持候选资源、资源不重叠、停机窗口、固定资源/时间、迟交与 makespan 目标。
- 发布验证：已形成本地三端启动、backend/solver 测试、release smoke 和发布收口记录。

当前主要差距不再是端到端链路是否成立，而是：真实业务数据入口、主数据口径、UAT 必需约束、Gantt 业务评审能力、审批治理和 UAT 收口材料尚未达到试点使用标准。

## 3. 下一阶段产品定位

下一阶段定义为：**从 POC baseline 到可 UAT 的 APS MVP**。

MVP 的成功标准不是覆盖所有高级 APS 场景，而是选定一个代表性试点范围，用真实或脱敏真实数据完成 2 轮以上 UAT，并让业务方能判断：

1. 输入数据是否可被系统稳定接收和校验。
2. 排程结果是否不违反 Must 级硬约束。
3. 延期、换型、资源利用率等关键结果是否可解释。
4. 版本发布、审批、回退、审计是否可追踪。
5. 系统是否具备进入下一轮试点优化的基础。

## 4. 产品目标

### 4.1 业务目标

1. 用真实或脱敏真实数据验证 APS 排程在化工批次生产场景中的业务可用性。
2. 建立 Recipe、Resource、Demand、Downtime 的最小主数据闭环。
3. 支撑排产员完成“导入/生成排产场景 → 求解 → 评审 → 提交审批 → 发布版本”的闭环。
4. 让生产管理人员能基于 KPI、Gantt、版本差异和发布说明评估排产方案。
5. 形成可复盘、可验收、可进入下一阶段高级约束建设的 UAT 结论。

### 4.2 用户目标

| 用户 | 下一阶段目标 |
| --- | --- |
| 排产员 | 能导入或生成真实排产场景，运行排程，查看 Gantt，定位异常任务，提交版本审批 |
| 审批者/生产管理 | 能查看版本差异、KPI、发布说明，审批或驳回排产方案 |
| 只读查看者 | 能查看已发布版本、Gantt 和关键指标，不误操作 |
| 管理员 | 能维护账号、角色、配置和关键操作审计 |
| 研发/算法 | 能用 UAT 样本回归约束、性能和失败原因 |

### 4.3 项目目标

1. 从样例数据驱动转向真实样本驱动。
2. 从“单次排程演示”转向“数据、求解、评审、治理、验收”的产品闭环。
3. 从应用内异步任务转向更稳定、可观测、可恢复的执行链路。
4. 从文档评审版转向 UAT 入口标准和验收标准。

## 6. 范围定义

### 6.1 已完成基线范围

- 登录、登出、会话校验、账号设置、中英双语。
- 样例排程、通用排程 API、异步任务、轮询状态。
- PostgreSQL 持久化 job、version、Gantt rows/bars/downtimes。
- 版本列表、Gantt、KPI、history、diff、发布、回退、release note 基础能力。
- CSV/Excel/JSON 导入导出基础能力。
- Gantt 缩放、拖拽草稿、锁定/解锁、冲突提示、试算。
- 发布验证脚本和本地 smoke。

### 6.2 下一阶段范围内

- 试点范围冻结：一个车间/产线、一个产品族、一个计划周期。
- UAT 样本包：真实或脱敏真实数据，含 Resource、Recipe、Demand、Downtime。
- 主数据导入：模板、字段校验、错误报告、导入版本记录。
- 排产场景生成：从主数据生成 solver 可用请求。
- Solver 必需约束增强：Demand + Recipe 展开 Operation、工序先后、基础换型、交期/优先级、失败原因分类。
- 异步执行稳定性：Redis-backed queue 或等价稳定队列方案、状态机、超时、失败、取消、可观测。
- Gantt 评审：按订单/产品/资源/异常定位，任务详情，迟交/固定/软约束提示。
- 版本治理：actor attribution、提交审批、审批通过/驳回、发布说明、回退语义、审计。
- 权限分级：管理员、排产员、审批者、只读查看者。
- UAT 与发布准备：测试计划、用例、缺陷分级、操作手册、验收报告。

### 6.3 下一阶段范围外

- 不覆盖所有车间、所有产品、所有工厂。
- 不做完整 ERP/MES 双向生产闭环。
- 不一次性实现复杂库存平衡、公用工程容量、人员班组、任务拆分/合批。
- 不承诺求解结果自动替代人工排产决策。
- 不把 Gantt 本地拖拽直接作为正式计划变更；正式变更需重新校验、重新求解或进入审批流程。

补充说明：

- 多工厂销产协同、集团层订单分配、持续交货拆单、供应商协同采购建议等能力已纳入后续候选方向，但不属于当前 MVP/UAT 阶段承诺。

## 7. 范围边界说明

| 边界主题 | 本项目负责 | 本阶段不负责 | 说明 |
| --- | --- | --- | --- |
| 主数据 | 定义最小对象、模板、校验和导入链路 | 正式主数据平台治理 | 先用文件/API 双通道支撑 UAT |
| ERP/MES 集成 | 定义接口契约、字段映射、Mock 数据和联调清单 | 正式生产系统双向闭环 | MVP 不依赖正式集成上线 |
| 排程求解 | 覆盖 UAT Must 约束和可解释失败原因 | 全量高级 APS 优化 | 复杂约束按试点价值排序 |
| Gantt 调整 | 支持评审、定位、草稿、试算 | 直接保存为正式计划 | 正式版本需治理流程 |
| 版本治理 | 审批、发布、说明、审计、回退语义 | 复杂多级审批/电子签 | 先满足 UAT 追溯要求 |
| 权限 | 基础角色和后端 API 校验 | 企业级 IAM/SSO | 先满足试点职责边界 |

| 角色 | 主要职责 | 关键权限 | 是否核心用户 |
| --- | --- | --- | --- |
| Admin | 用户、配置、数据和关键操作管理 | 全部权限、审计查看 | 是 |

## 9. 约束与假设

### 9.1 业务约束

- UAT 只选择一个代表性试点范围，不以全厂推广作为本阶段验收目标。
- Must 约束必须在 M0 冻结，避免进入开发后频繁变更。
- 真实样本必须有业务解释，不能只由研发拼凑。

### 9.2 技术约束

- 当前数据模型仍以排程请求和 Gantt 结果为主，主数据模型需要按 UAT 最小口径扩展。
- 当前求解器已有基础 CP-SAT 结构，但工序先后、换型、需求展开会显著增加建模复杂度。
- 当前前端是 vanilla JS 静态工作台，应优先复用现有状态管理和交互，不做大规模前端框架迁移。

### 9.3 项目假设

- 业务方能在 M0/M1 提供真实或脱敏真实样本。
- UAT 目标数据规模初期控制在 20-50 个资源、100-300 个工序任务、7-14 天 horizon。
- ERP/MES 正式联调可以后置，MVP 先通过文件导入和 API 契约完成验收。

## 11. 风险与待确认事项

| 编号 | 事项 | 影响 | 当前建议 |
| --- | --- | --- | --- |
| R-01 | 真实样本无法按时冻结 | 阻断主数据、Solver 和 UAT | M0 设置冻结日期，先用脱敏样本，缺口进入数据问题清单 |
| R-02 | 业务期望一次性完整 APS | 范围失控 | 用 Must/Should/Could 控制范围，只把 UAT 阻断项纳入 P0 |
| R-03 | 工序、换型、库存规则复杂度超预期 | Solver 延期 | 先做最小规则，复杂规则进入后续 backlog |
| R-04 | ERP/MES 边界不清 | 集成延期 | MVP 不依赖正式集成，先完成文件导入和 API 契约 |
| R-05 | Gantt 草稿被误认为正式计划 | 数据一致性风险 | 页面和流程明确草稿/正式边界 |
| R-06 | 权限只做前端隐藏 | 审计风险 | 后端 API 必须校验角色，关键动作必须记录 actor |

## 12. 结论

- 当前 POC baseline 已经具备继续推进的基础。
- 下一阶段应聚焦“真实数据、必需约束、评审治理、UAT 收口”，不宜同时追求完整 APS 和正式系统集成。
- 建议立即启动 M0/M1：冻结试点范围、约束优先级、真实样本包和主数据字段口径。
