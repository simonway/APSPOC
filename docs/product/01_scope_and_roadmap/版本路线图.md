## 2. 路线图原则

1. 先做真实数据入口，再做高级排程能力。
2. 先满足 UAT Must 约束，再扩大车间/产品范围。
3. 先把版本治理做可解释、可审批、可追溯，再谈正式下发闭环。
4. 先文件导入 + API 契约并行，正式 ERP/MES 集成后置。
5. 复用现有后端、solver、Gantt、版本和 smoke 基线，避免推翻重做。
6. 对高级 APS 约束采用 Must / Should / Could 分层，不一次性大而全。

## 3. 当前基线结论

### 3.1 V0 已具备能力

| 模块 | 当前能力 |
| --- | --- |
| 账户与访问 | 登录、登出、会话、账号设置、中英双语 |
| 排程主链路 | 样例排程、通用排程 API、异步 job、轮询、DONE/FAILED 状态 |
| 求解能力 | 候选资源、NoOverlap、停机窗口、固定资源/开始时间、迟交 + makespan 目标 |
| 持久化 | PostgreSQL job/version/Gantt rows/bars/downtimes、sourceRequestJson |
| Gantt | 版本 Gantt 展示、缩放、详情、停机、拖拽草稿、锁定/解锁、试算 |
| 版本治理 | version list、history、diff、release note、ready-for-release、publish、rollback、审计基础 |
| 导入导出 | 资源、任务、停机 CSV/Excel 导入，模板导出，JSON 请求导入 |
| 验证资产 | `verify-release.sh`、`release_smoke.py`、发布收口记录、本地 runbook |

### 3.2 V0 主要缺口

- 真实样本仍需冻结，当前仍更偏样例/演示。
- 主数据对象缺少 Recipe / Demand 的完整 MVP 口径。
- Solver 尚未覆盖完整工序先后、基础换型、Demand 展开。
- 异步执行仍需面向长耗时、多用户和失败恢复加固。
- Gantt 需要从“结果展示”升级为“业务评审工具”。
- 版本治理需要补齐 actor attribution、正式审批、角色权限和清晰 rollback 语义。
- UAT 文档、数据包、缺陷分级和操作手册需要收口。

### 3.3 2026-05 实施状态快照

相对本路线图初稿，当前真实状态已前进到以下阶段：

- `V1`：样本包、字段口径和演示范围已经基本收敛，可支撑当前 UAT 演示。
- `V2`：主数据导入与场景生成核心闭环已完成，`Resource / Recipe / Demand / Downtime / InventoryBalance / SetupRule` 均可进入系统并生成排产请求。
- `V3`：Solver UAT 最小约束核心闭环已完成，已覆盖 `Demand + Recipe -> Operation`、`precedence`、基础 `setupRules`、物料投入产出和库存约束的当前实现范围。
- `V4`：Gantt 评审和版本治理基础能力已具备，但正式审批流、角色权限、完整 actor attribution 尚未收口，因此只能定义为“部分完成”。
- `V5`：UAT 收口材料和正式发布前口径仍需继续补齐。

因此当前推荐对外口径为：

> V2/V3 核心能力已完成并可进入业务演示；V4/V5 产品化收尾未全部完成。

### 3.4 Snow Beer POC 五期规划口径（2026-05-12 补记）

针对 Snow Beer POC，当前已验证的能力主要集中在“智能包装计划排程”子场景，还不能等同于覆盖 Snow Beer POC 要求的全部业务场景。

后续三/四/五期边界调整为：

- **第三期：Snow Beer 主链路排程演示版**。目标是在第三期结束后，把 Snow Beer 从包装子场景推进到主业务链路可演示，覆盖需求、库存、包材、糖化、发酵、过滤、包装的离散化任务建模，以及基础前后置、换型、班次/停机、插单和不可行解释。
- **第四期：Snow Beer 全业务场景补齐版**。目标是在第四期结束后，补齐从第三期拆出的复杂业务场景，包括发酵成熟窗口、发酵罐容量/占用/不可混装、多锅次关系、过滤到清酒转换、清酒罐中转、静置/保鲜窗口、物料可用时间和全场景回归。
- **第五期：发布级产品化与正式 Release 准备版**。目标是在第五期结束后，补齐性能优化、审批与版本治理、UI/交互设计优化、稳定性、测试和发布治理；只有第五期 release gate 无阻断项后，才将 `pre-release` 推进为第一版正式 `release`。

第三期优先保证“主链路演示完整性”，第四期保证“全业务场景可演示、可解释”，第五期才承担正式发布质量门槛。

## 5. 版本详细说明

### V0：POC baseline（当前已具备）

#### 目标

证明“登录 → 导入/样例排程 → 异步任务 → 求解 → 版本沉淀 → Gantt 查看 → 版本治理 smoke”主链路成立。

#### 完成标志

- 本地三端服务可启动。
- backend/solver 单测通过。
- release smoke 覆盖登录、样例排程、版本 diff、模板导出、导入、发布、回退。
- 具备进入 MVP/UAT 规划的产品基础。

### V1：UAT 范围与数据冻结版

#### 目标

用一周左右时间完成 MVP 范围、真实样本、约束优先级和验收口径冻结。

#### 计划范围

- 选择一个试点车间/产线、产品族、计划周期。
- 明确目标数据规模：资源数、工序任务数、停机数、horizon。
- 冻结 Must / Should / Could 约束矩阵。
- 形成 UAT_v1 样本包和字段映射表。
- 明确 UAT 入口/出口标准和缺陷分级。

#### 明确不做

- 不同时覆盖多个业务范围。
- 不在样本未冻结前进入大规模开发。

#### 完成标志

- 业务、产品、研发、算法对试点边界和 Must 约束达成一致。
- UAT_v1 样本可被研发和算法用于导入/回归。

### V2：主数据导入 MVP

#### 目标

让真实或脱敏真实数据通过标准模板或 API 进入系统，并可生成排产场景。

#### 计划范围

- Resource、Recipe、Demand、Downtime 四类主数据最小模板。
- 字段类型、必填、引用关系、时间窗口、候选资源校验。
- 错误报告：成功行、失败行、字段、原因、建议修正。
- 导入版本记录：数据来源、导入人、导入时间、数据版本。
- 由导入数据生成排产请求，包括 horizon、目标权重、solver config。

#### 明确不做

- 不先做复杂主数据维护后台。
- 不以 ERP/MES 正式接入作为 V2 前置条件。

#### 完成标志

- UAT_v1 样本可通过导入链路进入系统。
- 非法数据不会进入排产主流程。
- 同一输入可以复现同一排产场景。

### V3：Solver UAT 约束版 / Snow Beer 主链路排程演示版

#### 目标

让求解结果满足真实 UAT 场景的 Must 级硬约束，并把 Snow Beer POC 从当前包装排程子场景推进到主业务链路可演示。第三期完成后，应至少可以按演示脚本展示 Snow Beer 从需求、库存、包材、糖化、发酵、过滤到包装的离散化主链路排程。

#### 计划范围

- Demand + Recipe 展开 Operation。
- 工序 precedence 约束。
- 基础 changeover / setup time。
- 固定资源、固定开始、停机窗口、交期/优先级的回归验证。
- Snow Beer 主链路样本：需求到生产任务、库存覆盖、包材齐套、糖化、发酵、过滤、包装线能力、包装换型、班次/停机、临时订单插单。
- 对糖化、发酵、过滤等环节先采用离散化固定时长任务建模，形成主链路演示闭环。
- 不可行、超时、资源不足、物料不足、窗口冲突等基础失败原因分类。
- Snow Beer 主链路演示脚本和回归测试。

#### 明确不做

- 不把发酵成熟窗口、清酒罐中转、连续流、浓度/收率、多锅次满罐等复杂行业规则作为第三期阻断项。
- 不把性能优化、正式审批治理和 UI 设计打磨作为第三期阻断项。
- 不追求所有复杂目标函数可配置。

#### 完成标志

- Snow Beer 主链路场景有可运行样本、演示路径和结果解释。
- UAT/Snow Beer 主链路样本可成功求解，或返回业务可理解的失败原因。
- P0/Must 硬约束不被违反。
- 复杂行业场景和发布级质量问题记录到第四期/第五期，不阻断第三期主链路演示结论。

### V4：Snow Beer 全业务场景补齐版

#### 目标

承接从第三期移出的复杂行业场景，补齐 Snow Beer POC 所有业务场景的可演示、可排程、可解释能力。第四期完成后，应能说明 Snow Beer POC 范围内每个业务场景如何建模、如何排程、哪些规则是精确支持、哪些规则是 POC 近似。

#### 计划范围

- 发酵成熟窗口的 POC 级建模。
- 发酵罐容量、占用、不可混装的最小可演示模型。
- 多锅次与发酵罐关系的近似或明确边界。
- 过滤到清酒的转换关系。
- 清酒罐中转、静置/保鲜窗口的 POC 级约束。
- 物料可用时间与缺料影响。
- 全场景样本包、全场景回归和业务解释。
- 明确连续流、浓度/收率、采购计划反推等仍后置的深水区能力。

#### 明确不做

- 不把发布级性能优化、正式审批治理和 UI 设计打磨作为第四期阻断项。
- 不新增超出 Snow Beer POC 范围的新行业场景，避免在全场景补齐阶段继续扩大业务范围。
- 不承诺生产级连续流、浓度/收率精确公式和采购计划自动反推一次性完整落地。

#### 完成标志

- Snow Beer POC 全业务场景均有样本、排程路径和业务解释。
- 对每个复杂行业规则，明确当前支持方式：精确支持、POC 近似或后置不承诺。
- 全场景样本可成功求解，或返回业务可理解的失败原因。
- 性能、审批治理、UI 精修和 release gate 统一进入第五期。

### V5：发布级产品化与正式 Release 准备版

#### 目标

在第四期 Snow Beer 全业务场景可演示、可解释的基础上，补齐第一版正式 release 所需的性能优化、审批治理、UI/交互设计优化、稳定性、测试和发布治理。第五期 release gate 无阻断项后，才将 `pre-release` 推进为第一版正式 `release`。

#### 计划范围

- Snow Beer 全场景样本的求解性能基线、超时策略和大样本回归。
- 异步执行稳定性、队列化、取消/重试、完整状态机和运行可观测性。
- Gantt 按订单、产品、资源、异常任务快速定位，补齐缺料、延期、换型、窗口冲突等业务高亮。
- 任务详情展示订单、产品、工序、时间、资源、固定状态、迟交、软约束影响。
- 版本 diff 强化 KPI、任务资源变化、时间变化、迟交变化。
- 审批流：提交审批、审批通过/驳回、发布已审批版本。
- actor attribution：创建人、提交人、审批人、发布人、回退人。
- release notes：发布原因、关键变化、风险说明、业务备注。
- 权限分级：Admin、Planner、Approver、Viewer。
- UI/交互设计优化、操作手册、全场景 smoke、release checklist、发布说明和回退方案。

#### 完成标志

- Snow Beer 全场景回归、性能基线、发布 smoke 和 UI 走查均通过。
- 一个正式发布版本能回答：谁创建、谁审批、谁发布、为什么发布、与上版差异是什么。
- 业务用户能在 5 分钟内定位一个订单的全部工序安排。
- pre-release 转正式 release 的检查清单、发布说明、操作手册和回退方案已齐备。
- 第五期 release gate 无阻断项后，才允许将 `pre-release` 推进为第一版正式 `release`。

### V6：高级 APS / 正式集成版（后续）

#### 候选范围

- 集团层多工厂协同计划：回答“做什么、做多少、在哪个厂做”。
- 集团层订单分配与多厂负荷平衡。
- 持续交货时间窗与任务自动拆分。
- 供应商限量、采购价、运输成本、采购建议协同优化。
- 集团层方案试算、利润目标比较和多版本经营分析。
- 复杂库存和投料平衡。
- 公用工程容量。
- 人员班组和班次。
- 任务拆分、合批、多目标优化。
- 正式 ERP/MES 双向集成和执行反馈闭环。
- 多车间、多产品、多工厂推广。

补充说明：

- 关于多工厂销产协同的详细规划，见：[多工厂APS未来能力规划.md](/Users/simon/Documents/MyProgramming/APSPOC/docs/product/01_scope_and_roadmap/多工厂APS未来能力规划.md:1)

#### 启动条件

- V5 UAT 形成明确试点结论。
- 高级约束有清晰业务价值排序。
- 真实数据和业务流程已稳定。

## 6. 建议实施顺序

| 顺序 | 主题 | 原因 |
| --- | --- | --- |
| 1 | 范围冻结 + UAT_v1 样本包 | 没有真实样本，后续导入、solver、UAT 都无法收口 |
| 2 | 主数据导入与校验 | 让真实数据稳定进入系统，是从演示到 UAT 的最大跨越 |
| 3 | Solver Must 约束 | 决定结果是否能被业务接受 |
| 4 | Gantt 评审与版本治理 | 决定业务是否能解释、审批和追踪方案 |
| 5 | 异步执行稳定性 | 支撑多人、多任务、长耗时 UAT |
| 6 | UAT 与发布收口 | 形成是否进入下一阶段的正式结论 |
| 7 | 高级 APS 与正式集成 | 基于试点反馈排序，而不是预设大而全 |

## 7. 版本依赖关系

```text
V0 POC baseline
  -> V1 UAT 范围与数据冻结
      -> V2 主数据导入 MVP
          -> V3 Solver UAT 约束 / Snow Beer 主链路排程演示
              -> V4 Snow Beer 全业务场景补齐
                  -> V5 发布级产品化与正式 Release 准备
                      -> V6 高级 APS / 正式集成
```

## 8. 关键决策点

| 决策点 | 影响阶段 | 当前建议 | 需要确认方 |
| --- | --- | --- | --- |
| UAT 试点范围选哪条线/哪个产品族 | V1 | 只选一个代表性范围 | 业务/产品/项目负责人 |
| 真实样本采用真实还是脱敏数据 | V1 | 优先脱敏真实数据 | 业务/数据负责人 |
| Recipe / Demand 最小字段口径 | V1/V2 | 先满足 UAT，不追求全量主数据 | 业务/产品/研发/算法 |
| 基础换型是否 Must | V3 | 由试点产品切换频率决定 | 业务/算法 |
| 发酵成熟窗口、清酒罐和多锅次关系采用精确建模还是 POC 近似 | V4 | 先满足客户演示，精确化进入后续深水区 | 产品/业务/研发/算法 |
| rollback 采用原版本重发还是复制为新草稿 | V5 | 推荐复制历史版本形成新草稿后审批发布 | 产品/业务/研发 |
| 是否试点前引入 Redis-backed queue | V5 | 若正式 release 涉及多人或长求解，建议纳入 | 研发/架构 |
| ERP/MES 首个联调系统 | V6 | MVP 先契约，不阻塞 UAT | IT/业务/研发 |

## 9. 建议下一步
