> 本路线图基于当前 APS POC 已实现能力制定，目标是把现有“可演示基线版本”逐步推进到“可支撑业务试点的最小可用版本”。

## 2. 路线图原则

- 先补真实业务入口，再补版本治理，再补集成与试点能力。
- 先解决“能不能用”，再解决“好不好管”和“能不能接入外围系统”。
- 尽量复用当前已实现的通用排产 API、版本模型和 Gantt 展示能力，避免重复推翻。
- 高级 APS 约束按试点业务必要性逐步引入，不做一次性大而全建设。

## 3. 当前基线结论

### 3.1 当前已实现（Phase 1 POC baseline）

- 登录、登出、会话校验、账号设置、中英双语。
- 样例排产闭环：发起排产、异步任务、轮询状态、生成版本。
- 通用排产任务提交 API。
- 版本列表、KPI、Gantt 结果查看。
- 版本发布。
- Gantt 本地草稿交互、缩放、冲突提示。

### 3.2 当前主要缺口

- 缺少真实业务录入页或最小主数据导入链路。
- 缺少版本 diff、发布历史、审计化 rollback。
- 缺少外部系统接入边界和试点非功能保障。
- 缺少换型、前后置、库存等高级 APS 约束能力。

## 4. 版本规划总览

| 版本 | 阶段定位 | 目标 | 交付重点 | 当前判断 |
| --- | --- | --- | --- | --- |
| V0 | POC 基线版 | 验证端到端排产闭环可行性 | 登录、样例排产、版本沉淀、Gantt、发布 | 已具备 |
| V1 | 最小业务建模版 | 让系统从“只会演示”变成“可接真实业务数据” | 真实建模入口、最小主数据接入、接口稳态 | 建议优先实施 |
| V2 | 版本治理增强版 | 让方案可比较、可回溯、可审计 | diff、rollback 语义、发布历史、权限边界 | 建议第二优先级 |
| V3 | 试点集成版 | 让系统具备试点落地条件 | 外部系统接入、执行架构增强、非功能补齐 | 建议第三优先级 |
| V4 | 高级优化版 | 贴近真实 APS 深水区场景 | 换型、工艺前后置、库存/物料等高级约束 | 视试点反馈决定 |

## 5. 各版本详细说明

### V0：POC 基线版（当前）

#### 目标

- 证明“登录 → 发起排产 → 任务完成 → 版本查看 → Gantt 展示 → 发布版本”这条主链路成立。

#### 已交付能力

- 统一工作台和双语登录。
- 样例排产和通用排产 API。
- 异步任务 + 轮询。
- PostgreSQL 版本持久化。
- Gantt 可视化和本地草稿交互。
- 单一已发布版本语义。

#### 不足

- 更适合演示，不足以支撑真实业务录入和试点运行。

### V1：最小业务建模版

#### 目标

- 让排产员能够在前端或通过最小导入方式提交真实业务场景，而不是只能运行样例。

#### 计划范围

- 新增真实业务建模入口，至少覆盖：场景名称、资源、任务、停机窗口、目标权重、求解参数。
- 确定最小主数据边界：优先明确 Resource、Task/Demand、Downtime 的来源。
- 固化通用排产 API 契约，作为前端录入页和外部系统共用接口。
- 完善输入校验和页面空态/错误态。
- 补充非功能最低要求：基础性能口径、错误可观测性、环境联调说明。

#### 明确不做

- 暂不引入复杂审批流。
- 暂不实现完整版本 diff/审计回滚。
- 暂不引入高级 APS 约束。

#### 完成标志

- 不依赖样例场景，也能创建并查看真实排产请求结果。
- 产品、研发、业务能就主数据来源形成一致口径。

### V2：版本治理增强版

#### 目标

- 让版本从“能看”升级到“能比较、能回退、能管理”。

#### 计划范围

- 明确 rollback 的真实业务语义。
- 新增版本 diff 能力，至少可比较 KPI、状态、任务分配变化。
- 增加发布历史和关键操作审计记录。
- 补充权限边界：至少区分排产员、审核/管理角色、只读角色。
- 评估是否将 Gantt 本地草稿升级为“提交调整并重新求解”的正式能力。

#### 明确不做

- 暂不处理外部系统下发闭环。
- 暂不解决全部高级约束。

#### 完成标志

- 用户能解释“为什么发布这个版本”和“如何回到历史版本”。
- 关键版本操作具备可追踪性。

### V3：试点集成版

#### 目标

- 让系统具备进入真实业务试点的最小工程条件。

#### 计划范围

- 明确 ERP/MES/主数据系统的输入输出边界。
- 补充外部系统对接说明和联调方案。
- 将当前应用内异步执行演进为更稳定的执行架构，例如 Redis 队列化。
- 补充非功能能力：数据规模验证、性能压测、可观测性、上线检查清单。
- 形成试点版 UAT、回归与上线准备材料。

#### 明确不做

- 暂不覆盖所有工厂场景。
- 暂不承诺复杂优化问题一次性解决。

#### 完成标志

- 至少完成一条真实业务试点链路。
- 系统在目标数据规模下可稳定演示和联调。

### V4：高级优化版

#### 目标

- 围绕真实业务痛点，逐步增强 APS 求解深度。

#### 候选范围

- 换型时间/changeover。
- 工艺前后置与多阶段路线。
- 物料/库存约束。
- 更丰富的目标函数配置和解释能力。

#### 是否启动条件

- 以试点反馈和业务价值排序为准，不默认直接启动。

## 6. 建议实施顺序

| 顺序 | 建议主题 | 原因 |
| --- | --- | --- |
| 1 | 真实建模入口 + 最小主数据边界 | 当前最大缺口，直接决定能否进入真实业务试点 |
| 2 | 非功能基线 + 接口稳态 | 防止录入能力补上后仍无法稳定联调 |
| 3 | 版本治理增强 | 直接决定业务是否敢确认和回退方案 |
| 4 | 外部系统接入 | 需要建立在数据和版本语义稳定之后 |
| 5 | 高级 APS 约束 | 需要由试点场景倒逼，不宜预先泛化 |

## 7. 版本依赖关系

```text
V0 POC 基线
  -> V1 最小业务建模版
      -> V2 版本治理增强版
          -> V3 试点集成版
              -> V4 高级优化版
```

## 8. 关键决策点

| 决策点 | 影响版本 | 当前建议 | 需要谁确认 |
| --- | --- | --- | --- |
| 真实录入优先还是主数据导入优先 | V1 | 优先做最小可用录入入口，同时明确主数据来源边界 | 产品/业务/研发 |
| rollback 是否独立于 publish | V2 | 独立定义，不再与 publish 共用语义 | 产品/业务/研发 |
| 是否引入细粒度权限 | V2 | 至少在版本治理阶段引入基本角色区分 | 产品/业务 |
| 是否升级执行架构 | V3 | 试点前评估切换到队列化执行 | 研发/架构 |
| 高级约束优先级 | V4 | 以试点真实痛点排序 | 业务/算法/研发 |

## 9. 建议下一步

- 并行补充 `非功能需求.md` 和 `外部系统对接说明.md`，避免后续试点方案反复改口。
- V2 之前先明确版本治理的业务语义，尤其是 publish、rollback、diff 三者关系。
