## 3. 当前已实现功能设计

### FD-01 登录与会话管理

- 入口：登录页、账号设置弹窗、登出按钮。
- 后端能力：认证、会话检查、登出、账号更新。
- 当前规则：除认证和健康检查外，大多数 `/api/v1/**` 需要登录。
- MVP 增强：会话响应需要支持角色/权限字段，供前端按钮显隐和后端权限校验使用。

### FD-02 样例排产触发

- 入口：工作台 `Run Sample Schedule`。
- 当前流程：点击按钮 → 后端生成样例场景 → 创建 job → 前端轮询 → 成功后生成版本。
- 保留价值：作为本地 smoke、演示、回归的稳定基线。
- MVP 要求：样例链路继续通过，不被主数据导入改造破坏。

### FD-03 通用排产任务 API

- 当前能力：接收 scenario、resources、tasks、downtimes、objectiveWeights、solverConfig。
- 当前校验：候选资源、停机窗口、固定资源等基础合法性。
- MVP 定位：主数据导入和场景生成最终仍应复用该排产入口，避免重复建设提交链路。

### FD-04 任务状态轮询

- 当前状态：PENDING、RUNNING、DONE、FAILED。
- MVP 目标状态：CREATED、QUEUED、RUNNING、SUCCEEDED、FAILED、TIMEOUT、CANCELLED。
- 设计要求：前端状态文案与后端枚举解耦，避免新增状态导致 UI 无法展示。

### FD-05 版本列表与结果查看

- 当前能力：版本列表、版本摘要、版本详情、KPI、Gantt。
- MVP 增强：支持按业务维度定位和筛选，例如订单、产品、资源、迟交、异常任务。
- 设计边界：版本数据以已持久化结果为准，Gantt 展示不得与后端版本不一致。

### FD-06 Gantt 本地交互与试算

- 当前能力：缩放、拖拽、本地草稿、锁定/解锁、冲突提示、试算、拖拽开始/结束时间悬浮卡片。
- MVP 规则：本地草稿不是正式版本；正式变更需要重新求解、生成新版本并进入治理流程。
- 设计要求：所有草稿状态必须有明确视觉提示；拖拽中的时间提示不得被任务条遮挡。

### FD-07 版本治理基础

- 当前能力：release note、ready-for-release、publish、rollback、history、diff、audit 基础；点击 diff 任务后可自动定位到当前版本任务条或相关资源行，并给出状态反馈。
- MVP 增强：审批通过后发布，记录创建人、提交人、审批人、发布人、原因和差异。
- 回退建议：复制历史版本形成新草稿，重新审批后发布。

## 4. MVP/UAT 新增功能设计

### FD-09 主数据导入 MVP

#### 目标

让真实或脱敏真实数据以标准模板进入系统。

#### 输入对象

- Resource：资源/设备。
- Recipe：产品工艺路线与工序。
- Demand：订单/需求/批次计划。
- Downtime：停机/检修/不可用窗口。

#### 关键设计

- 支持 CSV/Excel 模板。
- 校验必填、类型、枚举、引用、重复 ID、时间窗口。
- 返回 ImportBatch 与 ImportError。
- 校验失败不得进入排程主流程。
- 导入成功生成 dataVersion。

#### 验收标准

- UAT_v1 样本可导入。
- 错误能定位到 sheet、行、字段和原因。
- 导入结果可追溯导入人、时间和来源。

### FD-10 排产场景生成

#### 目标

将 Demand + Recipe 转换成 solver 可排程的 Operation/Task。

#### 关键设计

- Demand 关联 productCode。
- Recipe 按 productCode 和 sequence 展开 Operation。
- Operation 继承 duration、candidateResourceIds、setupGroup。
- 生成 predecessorOperationIds 表达工序先后。
- 生成 scenarioName、horizon、objectiveWeights、solverConfig。

#### 验收标准

- 同一 dataVersion 可复现同一场景。
- 缺少 Recipe 或资源引用非法时拒绝生成。
- 生成场景可提交到现有排产 API。

### FD-11 Solver Must 约束增强

#### 目标

覆盖 UAT 必须遵守的硬约束。

#### 关键设计

- precedence：后序 Operation 开始 >= 前序结束。
- setup：同资源相邻 setupGroup 变化时插入 setupMinutes。
- failureReason：不可行、超时、资源不足、数据非法、未知异常。
- 回归样本：以 UAT_v1 样本为基础。

#### 验收标准

- Must 硬约束 100% 不违反。
- 求解失败有业务可理解原因。
- 目标规模常规场景 5 分钟内返回。

### FD-12 异步执行稳定性

#### 目标

支撑多人、多任务和长耗时求解。

#### 关键设计

- 引入 Redis-backed queue 或等价稳定队列方案。
- 状态机扩展为 CREATED/QUEUED/RUNNING/SUCCEEDED/FAILED/TIMEOUT/CANCELLED。
- 记录 jobId、requestId、队列时间、求解耗时、失败原因。
- 支持超时、取消和可配置并发。

#### 验收标准

- 多任务连续提交状态不丢失。
- solver 不可达/超时有明确终态。
- UAT 期间可按 jobId 定位问题。

### FD-13 Gantt 业务评审

#### 目标

让 Gantt 成为业务评审工具，而不仅是技术展示。

#### 关键设计

- 筛选：订单、产品、资源、迟交、冲突、固定任务。
- 定位：点击差异或异常任务自动定位到 Gantt；若当前版本已无对应任务条，则退化定位到相关资源行。
- 详情：展示订单、产品、工序、资源、时间、交期、迟交、setup 影响。
- 对比：从 diff 进入任务变化，并对 `ADDED` / `MODIFIED` / `REMOVED` 任务提供差异化高亮和明确状态反馈。
- 交互反馈：拖拽中的时间提示使用悬浮卡片样式，保证在高亮任务条上方仍可读。

#### 验收标准

- 业务用户 5 分钟内能定位一个订单全部工序。
- 迟交、固定、停机、setup 影响可识别。
- diff 任务点击后，至少有“任务条高亮 / 资源行高亮 / 状态区提示”三者之一明确出现。
- 拖拽时开始/结束时间卡片清晰可见，不被任务条或辅助高亮遮挡。
- 版本切换后展示与后端数据一致。

### FD-14 审批与角色权限

#### 目标

让发布成为受控业务动作。

#### 关键设计

- 角色：Admin、Planner、Approver、Viewer。
- 流程：DRAFT → SUBMITTED/READY_FOR_RELEASE → APPROVED → RELEASED。
- 审批事件：submit、approve、reject、publish、rollback。
- 后端 API 必须校验角色，不能只靠前端隐藏按钮。

#### 验收标准

- 未审批版本不能正式发布。
- 关键动作记录 actor、时间、备注和前后状态。
- Viewer 不能创建、审批或发布。

### FD-15 UAT 与发布收口

#### 目标

让验收可执行、可记录、可复盘。

#### 关键设计

- UAT 数据包与用例绑定。
- 缺陷分级：P0/P1/P2/P3。
- 每日 triage：负责人、状态、修复版本、验证结果。
- 发布检查：自动化测试、smoke、UI 人工走查、文档确认。

#### 验收标准

- 核心用例通过率 100%。
- P0 缺陷为 0。
- P1 缺陷有规避方案和修复计划。

## 6. 研发实现关注点

- 前端：优先复用当前 `app.js` 状态管理和 Gantt 交互，不做框架迁移。
- 后端：复用现有 `ModelImportService`、`SchedulingJobService`、`VersionService` 和 `PostgresScheduleStore`。
- Solver：复用现有 CP-SAT 可选 interval、NoOverlap、pinned、downtime 和目标函数结构。
- 数据：新增 Recipe/Demand/Operation 时需保持与现有 Task/Gantt 契约兼容。
- 治理：审批、发布、回退、审计需优先统一业务语义，再落地接口。
