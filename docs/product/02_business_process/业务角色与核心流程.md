## 2. 业务角色

| 角色 | 所属部门 | 核心职责 | 当前痛点 | MVP/UAT 目标 |
| --- | --- | --- | --- | --- |
| Planner / 排产员 | 生产计划/计划运营 | 导入数据、创建排程、查看方案、提交审批 | 当前只有样例入口，缺少真实数据主链路 | 能基于真实样本完成排程与评审 |
| Approver / 审批者 | 生产管理/调度 | 评估方案、审批/驳回、发布版本 | 当前版本治理基础已具备，但审批语义和角色边界需强化 | 能基于版本差异和 release note 做审批 |
| 生产管理 | 生产管理/运营 | 判断方案是否可用于试点 | 当前缺少真实样本和 Must 约束验收口径 | 能依据 KPI、Gantt 和差异判断是否通过 UAT |
| Viewer / 只读用户 | 管理层/业务观察者 | 查看已发布结果和关键指标 | 当前登录后默认拥有过多操作权限 | 只读查看，不误操作 |
| Admin / 系统管理员 | IT/系统支持 | 账号、权限、运行配置、排障支持 | 当前只有基础账号维护能力 | 能保障环境、权限和审计可用 |
| 算法/研发支持 | 研发/算法 | 维护规则、分析失败、回归样本 | 真实业务 Must 约束和失败原因口径仍需收敛 | 能用 UAT 样本快速定位问题 |

## 3. 关键业务对象

| 对象 | 定义 | 当前来源 | MVP/UAT 来源 |
| --- | --- | --- | --- |
| Resource | 承载任务的设备/产线/罐/过滤/干燥等资源 | 样例数据或请求体 | 模板导入/后续主数据系统 |
| Recipe | 产品工艺路线和工序模板 | 当前无正式对象 | 模板导入/工艺台账 |
| Demand | 订单/需求/批次计划 | 当前无正式对象 | 模板导入/后续 ERP |
| Downtime | 资源不可用窗口 | 样例数据或请求体 | 模板导入/后续 MES/日历 |
| ScheduleJob | 一次异步排程任务 | 后端生成 | 后端生成 |
| ScheduleVersion | 一次成功求解后的结果快照 | 后端生成 | 后端生成，并纳入审批治理 |
| GanttData | 版本可视化结果 | 后端派生 | 后端派生，增加业务评审能力 |
| AuditEvent | 关键操作审计 | 已有基础 | 增强 actor attribution 和审批事件 |

## 4. 当前流程（As-Is / 已跑通基线）

### 4.1 当前流程概述

当前系统已实现的 POC baseline 流程是：

```text
登录
  -> 运行样例排产 / 提交通用排产请求
    -> 后台异步求解
      -> 前端轮询任务状态
        -> 成功生成版本
          -> 查看 KPI / Gantt / history / diff
            -> 保存说明 / 提交待发布 / 发布 / 回退
```

它已经证明：

- 三层架构链路成立。
- 版本和 Gantt 可持久化和展示。
- 基础治理 smoke 可执行。

但它仍偏演示，不足以完成真实业务 UAT。

### 4.2 当前流程步骤

| 步骤 | 发起角色 | 输入 | 系统动作 | 输出 | 当前缺口 |
| --- | --- | --- | --- | --- | --- |
| A0 | 用户 | 用户名/密码 | 登录并校验会话 | 工作台或错误提示 | 角色权限仍粗粒度 |
| A1 | 排产员 | 点击样例排产或提交 API | 创建异步 job | jobId、任务状态 | 缺少真实数据入口 |
| A2 | 系统 | resources/tasks/downtimes/权重/参数 | 调用 solver 求解 | FEASIBLE/OPTIMAL 或失败 | 缺少 Recipe/Demand/precedence/setup |
| A3 | 系统/排产员 | jobId | 前端轮询状态 | DONE/FAILED 和 versionId | 进度表达和失败分类需增强 |
| A4 | 系统 | 求解结果 | 生成 DRAFT 版本并落库 | 版本、Gantt、KPI | 真实样本可用性需验证 |
| A5 | 排产员/生产管理 | 版本/Gantt | 查看 KPI、Gantt、diff、history | 结果评审 | Gantt 业务评审能力需增强 |
| A6 | 生产管理 | 选中版本 | 保存说明、提交待发布、发布/回退 | 当前生效版本 | 审批语义和角色边界需强化 |

## 5. 目标流程（To-Be / MVP-UAT）

### 5.1 流程目标

从“可演示的排程闭环”升级为“可基于真实或脱敏真实样本完成 UAT 的业务闭环”。

### 5.2 目标流程主链路

```text
登录系统
  -> 导入/准备 UAT_v1 样本
    -> 校验并生成 dataVersion
      -> 由 Demand + Recipe 生成排产场景
        -> 创建异步排程任务
          -> 查看任务状态与失败原因
            -> 生成 DRAFT 版本
              -> 通过 Gantt / KPI / diff 评审方案
                -> Planner 提交审批
                  -> Approver 审批/驳回
                    -> 发布正式版本
                      -> 形成 UAT 结论或进入下一轮试算
```

### 5.3 目标流程步骤

| 步骤 | 发起角色 | 系统动作 | 人工动作 | 输出 | 是否自动化 |
| --- | --- | --- | --- | --- | --- |
| T0 | 产品/业务/项目负责人 | 冻结试点范围与 Must 约束 | 确认范围、数据、验收标准 | UAT 入口标准 | 否 |
| T1 | Planner | 导入 Resource/Recipe/Demand/Downtime | 准备数据并触发导入 | dataVersion、错误报告 | 部分自动 |
| T2 | 系统 | 校验数据并生成场景 | 处理错误或确认场景 | 可提交求解的 scenario | 是 |
| T3 | Planner | 提交排程 job | 选择参数、发起排程 | jobId、状态机 | 是 |
| T4 | 系统 | 调用 solver、记录状态/耗时/失败原因 | 等待或取消 | SUCCEEDED/FAILED/TIMEOUT 等终态 | 是 |
| T5 | Planner/生产管理 | 查看版本、Gantt、diff、异常任务 | 评审方案、定位问题 | 候选版本集 | 否 |
| T6 | Planner | 提交审批 | 补充 release note/说明 | 待审批版本 | 否 |
| T7 | Approver | 审批/驳回/发布 | 记录原因与风险 | 正式版本或驳回意见 | 否 |
| T8 | 测试/业务/项目负责人 | 执行 UAT 用例 | 记录缺陷与结论 | UAT 报告 | 否 |

## 6. 核心业务场景

| 场景编号 | 场景名称 | 触发条件 | 参与角色 | 期望结果 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| SC-00 | 登录进入工作台 | 用户打开系统 | 全部用户 | 成功进入工作台并加载当前数据 | P0 |
| SC-01 | 样例排产 baseline | 需要验证系统可用 | Planner/研发支持 | 样例排产稳定可运行 | P0 |
| SC-02 | 导入 UAT 样本 | 进入真实样本阶段 | Planner/Admin | 数据通过校验并生成 dataVersion | P0 |
| SC-03 | 生成排产场景 | 导入通过后 | Planner | 得到 solver 可用的 scenario | P0 |
| SC-04 | 提交排程与查看状态 | 场景准备完成 | Planner | 得到 version 或明确失败原因 | P0 |
| SC-05 | 评审版本与 Gantt | version 生成后 | Planner/Approver/生产管理 | 能比较方案并定位问题 | P0 |
| SC-06 | 提交审批与发布 | 候选版本确认后 | Planner/Approver | 正式版本发布并可追溯 | P0 |
| SC-07 | 回退/复制历史版本 | 需恢复历史方案时 | Approver/Admin | 形成可审计的新草稿或回退结果 | P1 |
| SC-08 | UAT 收口 | 核心用例执行后 | 测试/业务/项目负责人 | 输出通过/有条件通过/不通过结论 | P0 |

## 7. 关键业务规则入口

| 规则主题 | 规则描述 | 在流程中的位置 |
| --- | --- | --- |
| Must 约束 | 资源能力、停机、固定资源/开始、工序先后、基础换型不得违反 | T2-T4 |
| 数据版本追溯 | 导入、场景、job、version 可串联 | T1-T5 |
| 角色权限 | Planner/Approver/Viewer/Admin 权限边界明确 | T0-T7 |
| 审批发布 | 未审批版本不得正式发布 | T6-T7 |
| 正式版本唯一 | 同一时刻最多一个 RELEASED 版本 | T7 |
| 草稿边界 | Gantt 本地草稿不等于正式版本 | T5 |

## 8. 异常与分支流程

| 异常编号 | 异常场景 | 触发条件 | 处理方式 | 责任角色 |
| --- | --- | --- | --- | --- |
| EX-01 | 登录失败 | 用户名密码错误、服务不可达 | 返回登录错误 | 用户/Admin |
| EX-02 | 导入校验失败 | 缺字段、引用错误、时间错误 | 返回行/字段级错误，不生成场景 | Planner |
| EX-03 | 场景生成失败 | Recipe/Demand 无法匹配 | 不进入排程，提示缺口 | Planner/业务 |
| EX-04 | 求解失败 | 不可行、超时、solver 不可达 | job 终态失败并记录 failureReason | Planner/算法/研发 |
| EX-05 | 权限不足 | Viewer 或未授权用户执行关键动作 | 返回 PERMISSION_DENIED | 用户/Admin |
| EX-06 | 审批驳回 | 版本不满足业务要求 | 回到草稿或重新试算 | Planner/Approver |
| EX-07 | Gantt 草稿冲突 | 本地拖拽与任务/停机重叠 | 前端高亮冲突，不自动保存 | Planner |

## 9. 对产品和研发的要求

### 9.1 对产品的要求

- 必须先冻结试点范围、样本口径和 Must 约束，再进入大规模实施。
- 必须明确审批、发布、回退和正式版本的业务语义。
- 必须持续区分“POC baseline 已实现”和“MVP/UAT 待建设”边界。

### 9.2 对研发/算法的要求

- 保持 baseline 样例链路稳定，避免被新功能改坏。
- 所有导入/场景/求解失败必须有可理解原因和可定位信息。
- Must 约束通过真实样本回归，而不是只通过样例验证。

### 9.3 对数据和接口的要求

- Resource、Recipe、Demand、Downtime 的权威来源和字段映射要明确。
- API 契约要支持导入、场景生成、审批和状态扩展。
- 正式版本和 dataVersion 需要能跨文档、跨接口追溯。
