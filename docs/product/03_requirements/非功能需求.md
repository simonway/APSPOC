> 本文档定义 APS POC 从当前基线版本推进到试点阶段所需的非功能要求。当前重点是为下一阶段建设提供质量门槛，而不是一次性定义完整生产级 SLA。

## 2. 适用范围

- 适用于当前三层结构：前端工作台、Spring Boot 后端、Python OR-Tools 求解器。
- 适用于登录认证、排产任务提交、异步轮询、版本查看、Gantt 展示、版本发布等当前核心能力。
- 当前不包含对大型生产环境、跨机房高可用、完整企业级审计和多组织权限体系的承诺。

## 3. 非功能设计原则

- 优先保证“可稳定演示、可进入试点”，再逐步提高到更强工程标准。
- 优先约束系统边界行为，例如性能、错误反馈、权限、数据一致性。
- 对尚未验证的数据规模和集成场景，不做虚高承诺，先定义最低可接受门槛。
- 对会影响业务信任的问题，例如版本语义、草稿状态、错误提示，要有清晰可见的系统反馈。

## 5. 详细要求

### NFR-01 提交与查询响应性能

#### 要求

- 登录、会话检查、版本列表、版本摘要、Gantt 数据等接口在正常环境下应保持秒级响应。
- 创建排产任务接口只负责创建 job，不应同步等待求解完成。
- 前端结果查看不能因为求解执行而阻塞页面交互。

#### 当前实现依据

- 创建排产任务采用异步方式，前端通过轮询获取结果。
- 工作台刷新和版本切换已与求解执行解耦。

#### 后续建议

- 在试点前定义更具体的响应时间门槛，并准备标准数据集验证。

### NFR-02 求解性能

#### 要求

- 默认求解配置下，系统应能在合理时间内返回可行解或明确失败结果。
- 对超时、无解、求解器异常等情况，应返回明确状态，不允许无限等待。

#### 当前实现依据

- 当前默认配置为 `timeLimitSeconds=10`、`numSearchWorkers=4`。
- 失败结果会写回任务状态并附带错误信息。

#### 后续建议

- 为 V1/V3 阶段分别准备“样例数据量”和“试点数据量”的性能基线。

### NFR-03 可用性与稳定性

#### 要求

- 登录、样例排产、轮询、版本查看、Gantt 展示、发布版本这条主链路应可重复运行。
- 服务异常时，系统应进入可恢复状态，而不是卡死或页面失真。
- 任务和版本应在系统重载后可继续查询。

#### 当前实现依据

- 后端有健康检查接口。
- 任务与版本结果持久化到 PostgreSQL。

#### 后续建议

- 试点前补充任务执行架构稳定性评估，必要时升级到队列化执行。

### NFR-04 安全与访问控制

#### 要求

- 除健康检查和认证入口外，其余业务接口必须在登录态下访问。
- 修改账号信息时必须校验当前密码。
- 当前阶段至少保证“登录态隔离”，下一阶段补角色权限边界。

#### 当前实现依据

- 前端通过 Session Cookie 访问后端。
- 会话失效时会清空工作台状态并返回登录页。

#### 后续建议

- 在版本治理阶段引入排产员、审核/管理、只读等基础角色。

### NFR-05 审计与可追溯性

#### 要求

- 系统至少要保留一次排产任务和对应版本的可追溯记录。
- 发布版本时，必须能识别当前生效方案。
- 后续版本需要补关键操作审计，尤其是发布、回滚、账号修改。

#### 当前实现依据

- 已保留 `jobId`、`versionId`、`createdAt`、`publishedAt` 等关键信息。
- 发布后旧的已发布版本会归档。

### NFR-06 数据一致性

#### 要求

- 同一时刻只允许一个当前已发布版本。
- 前端本地草稿必须与后端已保存版本严格区分。
- 输入数据引用关系必须合法，例如候选资源、停机资源必须真实存在。

#### 当前实现依据

- 发布接口会将历史已发布版本转为 `ARCHIVED`。
- 本地 Gantt 草稿不回写后端。
- 请求校验会拒绝非法资源引用和非法停机窗口。

### NFR-07 失败可见性

#### 要求

- 登录失败、会话失效、求解失败、轮询失败、发布失败、账号修改失败等场景都必须有明确反馈。
- 前端不允许 silently fail。

#### 当前实现依据

- 当前登录页、任务状态卡片、账号设置弹窗均已有错误提示机制。

### NFR-08 可观测性

#### 要求

- 至少有健康检查能力。
- 关键任务、失败原因、版本生成结果应能被研发和联调方快速定位。
- 试点前建议明确日志、基础监控和故障定位口径。

#### 当前实现依据

- 当前有 `/api/v1/health` 和任务状态查询。

#### 后续建议

- 增加任务执行日志、求解耗时记录、关键错误分类。

### NFR-09 易用性与国际化

#### 要求

- 关键页面必须具备加载态、空态、错误态和成功反馈。
- 核心流程语言切换要即时生效。
- 用户操作后应看到清晰结果，例如“已登出”“发布成功”“草稿已重置”。

#### 当前实现依据

- 登录页和主工作台支持中英切换。
- 当前页面已覆盖主要空态和错误态。

### NFR-10 可维护性与扩展性

#### 要求

- 新增建模入口、版本治理或外部系统接入时，应尽量复用当前通用排产 API 和版本结构。
- 重要对象（任务、版本、Gantt、KPI）的字段语义应保持稳定。

#### 当前实现依据

- 后端编排服务和求解器已通过请求/响应模型解耦。

### NFR-11 兼容性与部署约束

#### 要求

- 前端、后端、求解器的端口和运行方式在团队内保持统一。
- 默认测试账号、环境启动方式和样例请求应在文档中明确。

#### 当前实现依据

- 当前已定义本地端口：8080/8081/8000。
- README 已提供 Docker/Homebrew 启动方式和默认账号。

### NFR-12 测试保障

#### 要求

- 核心链路必须具备稳定的回归清单。
- 试点前应至少具备：认证单元测试、求解器单元测试、接口联调清单、UI 手工回归清单。

#### 当前实现依据

- 已有认证服务测试和求解器停机约束测试。
- 验收文档已建立第一版测试用例和回归清单。

## 6. 优先级建议

| 优先级 | 主题 |
| --- | --- |
| P1 | 提交/查询性能、可用性、安全、数据一致性、失败可见性 |
| P2 | 审计、可观测性、测试保障、国际化体验 |
| P3 | 更高等级部署标准、企业级权限体系、完整生产级 SLA |

## 7. 验收建议

- 在进入 V1 之前，先确认 P1 级非功能要求已被团队接受。
- 在进入 V3 试点集成前，补齐可观测性、非功能基线和最小回归方案。
- 在每个里程碑评审时，用本文件逐项确认“已满足 / 部分满足 / 未满足”。
