## 2. 适用范围

- 前端静态工作台、Spring Boot 后端、Python OR-Tools 求解器。
- 登录认证、数据导入、排产任务、异步执行、版本/Gantt、审批发布、UAT 验证。
- PostgreSQL 持久化和 Redis-backed queue 或等价稳定执行方案。
- 不包含跨机房高可用、完整企业 IAM、正式 ERP/MES 双向生产闭环的 SLA 承诺。

## 3. 非功能设计原则

1. 优先保证 UAT 主链路稳定，而不是追求生产级大而全。
2. 所有系统边界行为必须可解释：输入错误、求解失败、超时、权限不足、版本状态不合法。
3. 正式版本必须可追溯：谁创建、谁提交、谁审批、谁发布、为什么发布。
4. 真实样本下的性能和稳定性必须以固定数据包验证。
5. 前端交互必须明确区分“本地草稿”和“已保存/已发布版本”。
6. Snow Beer 第三期的非功能目标以“主链路可演示”为主，允许记录复杂行业场景、性能和体验问题进入第四/第五期。
7. Snow Beer 第四期的非功能目标以“全业务场景可演示、可解释”为主，仍不承担正式 release 门禁。
8. Snow Beer 第五期的非功能目标以“发布级稳定、可追溯、可操作”为主，作为 `pre-release` 转正式 `release` 的基础门槛。

## 5. 性能要求

### 5.1 查询与提交性能

- 登录、会话检查、版本列表、版本详情、Gantt 数据查询应保持秒级响应。
- 创建排产任务应异步返回，不同步等待 solver 结束。
- 前端不得因后台求解阻塞页面操作。

### 5.2 求解性能

MVP 初始目标规模：

| 指标 | 目标 |
| --- | --- |
| 资源数 | 20-50 |
| 工序任务数 | 100-300 |
| 排产周期 | 7-14 天 horizon |
| 常规求解时间 | 5 分钟内返回可行结果或明确失败 |
| 超时处理 | 返回 TIMEOUT 或明确失败分类，不无限等待 |

### 5.3 前端展示性能

- 目标规模 Gantt 可正常滚动、筛选、定位。
- 版本切换和筛选操作不应导致页面卡死。
- 若数据量超出前端可承载范围，应有加载提示或降级策略。

## 6. 稳定性与可用性要求

- 核心链路：登录 → 导入 → 创建场景 → 排程 → 版本生成 → Gantt 查看 → 提交审批 → 发布，必须可重复执行。
- 后端重启后，已完成任务和版本仍可查询。
- 未完成任务在重启后需要有明确处理策略：恢复、失败标记或重新排队。
- Solver 不可达、超时、不可行、数据非法时，job 状态和错误信息必须明确。
- 多个排程任务连续提交时，不允许状态互相覆盖或结果串扰。

## 7. 安全与权限要求

- 未登录用户仅可访问登录、会话、登出、健康检查和静态资源。
- 已登录用户根据角色访问功能：Admin、Planner、Approver、Viewer。
- 创建排程、导入数据、提交审批、审批、发布、回退等关键动作必须后端校验。
- 不能只依赖前端隐藏按钮实现权限。
- 账号修改必须校验当前密码。
- 默认账号仅用于本地/试点环境，正式部署前需替换。

## 8. 审计与追溯要求

关键事件必须记录：

| 事件 | 必要字段 |
| --- | --- |
| 导入数据 | 数据版本、导入人、导入时间、来源、成功/失败行数 |
| 创建排程 | jobId、scenario、创建人、创建时间、数据版本 |
| 求解完成/失败 | jobId、solver 状态、耗时、失败原因、versionId |
| 提交审批 | versionId、提交人、提交时间、备注 |
| 审批/驳回 | versionId、审批人、审批时间、意见 |
| 发布 | versionId、发布人、发布时间、release notes、前一发布版本 |
| 回退 | 目标版本、操作人、原因、前后状态 |
| 账号修改 | 操作人、时间、结果 |

## 9. 数据一致性要求

- 导入数据版本、排产场景、solver 请求、版本结果之间需要可追溯。
- 同一数据版本重复生成场景应可复现。
- 当前正式发布版本必须唯一。
- 本地草稿、试算版本、正式发布版本必须在 UI 和数据状态上明确区分。
- Gantt 展示必须与后端版本数据一致。
- 任务候选资源、停机资源、Recipe 引用、Demand 引用必须合法。

## 10. 失败可见性要求

失败信息分两层：

1. **用户可理解**：例如“导入第 12 行资源编号为空”“该需求无可用设备”“求解超时，请缩小范围或延长时间”。
2. **研发可定位**：包含 jobId、requestId、错误分类、服务日志时间、solver 状态。

关键失败分类：

- AUTH_REQUIRED：未登录或会话失效。
- PERMISSION_DENIED：角色权限不足。
- IMPORT_VALIDATION_FAILED：导入校验失败。
- INVALID_SCENARIO：排产场景非法。
- INFEASIBLE：约束不可满足。
- SOLVER_TIMEOUT：求解超时。
- SOLVER_UNAVAILABLE：求解器不可达。
- EXECUTION_FAILED：执行异常。

## 11. 可观测性要求

MVP/UAT 期间至少需要：

- 健康检查：frontend、backend、solver。
- 后端 job 状态查询。
- solver 调用耗时和状态。
- 失败原因分类和错误摘要。
- 队列长度/运行中任务数，如果接入队列。
- `.runtime/logs` 或等价日志位置说明。
- release smoke 汇总结果。

## 12. 易用性与国际化要求

- 登录、导入、排程、Gantt、审批发布都需要加载态、空态、错误态和成功反馈。
- 中英文切换后核心页面文案一致，不出现明显漏翻。
- 导入错误要以业务字段和行号呈现，不只展示技术异常。
- 审批、发布、回退等高影响动作需二次确认或明确提示。
- Gantt 草稿必须明确提示“未保存/非正式版本”。

## 13. 测试保障要求

| 测试层级 | MVP/UAT 要求 |
| --- | --- |
| backend 单元测试 | 认证、导入、版本治理、trial solve、状态约束 |
| solver 单元测试 | 资源、停机、固定任务、precedence、setup、不可行场景 |
| API 集成测试 | 登录、导入、排程、版本、审批、发布、回退 |
| smoke 测试 | 基于 `scripts/verify-release.sh` 和 `scripts/release_smoke.py` 扩展 |
| UI 人工走查 | 登录、语言、导入、Gantt 拖拽/定位/锁定、审批发布 |
| UAT 测试 | 使用 UAT_v1 样本包执行端到端用例 |

## 14. Snow Beer 三/四/五期非功能边界

### 14.1 第三期非功能边界

第三期的非功能验收服务于“主链路可演示”：

- Snow Beer 主链路场景有固定样本、执行步骤、预期结果和业务解释。
- 求解可以在演示可接受时间内完成；若未达到发布级性能，记录为第五期性能优化项。
- UI 可以支撑主链路演示路径，不要求完成最终视觉和交互 polish。
- 审批和角色权限可以沿用当前基础治理能力，不作为第三期阻断项。
- 不可行场景必须有业务可理解原因，不能只暴露底层 `INFEASIBLE`。

### 14.2 第四期非功能边界

第四期的非功能验收服务于“全业务场景可演示、可解释”：

- 每个 Snow Beer POC 场景都有固定样本、执行步骤、预期结果和业务解释。
- 复杂行业规则需要明确当前支持方式：精确支持、POC 近似或后置不承诺。
- 全场景样本需要可回归，但不要求达到正式 release 性能基线。
- UI 可以支撑全场景演示路径，不要求完成最终发布级 polish。

### 14.3 第五期非功能边界

第五期的非功能验收服务于“pre-release 转正式 release”：

- Snow Beer 全场景样本形成性能基线，并纳入回归。
- 异步执行具备队列、超时、取消/重试、完整状态机和可观测信息。
- 审批、发布、回退、actor attribution 和审计字段满足第一版正式发布要求。
- UI 完成业务场景入口、异常高亮、方案对比、导入错误和 Gantt 评审体验优化。
- release checklist、操作手册、发布说明、回退方案和 smoke 记录齐备。

## 15. 验收建议

- M0 结束时：确认性能目标、角色权限、审计字段和 UAT 缺陷分级是否已被接受。
- M3 结束时：用真实样本验证求解性能和 Must 约束。
- M5 结束时：验证审批、发布、回退、actor 和 Gantt 评审体验。
- M6 结束时：确认核心用例通过率 100%、P0 缺陷为 0、P1 缺陷有规避方案。
