> 本计划将 APS 下一阶段定义为“从 POC baseline 到可 UAT 的 MVP”，按 8-10 周节奏拆成可执行里程碑和工作包。

## 2. 计划假设

- 当前基线能力已稳定：登录、样例排程、通用排程 API、版本/Gantt、导入导出、发布治理 smoke。
- POC 已完成，下一阶段不再以“演示优化”为主要目标，而以“UAT 可用”为主要目标。
- 业务方能提供一个代表性试点范围和一套真实或脱敏真实样本。
- 计划按 1-3 周粒度拆分，允许研发、算法、产品并行推进。
- 复杂高级 APS 能力不作为当前阶段前提。

## 3. 总体目标

在 8-10 周内完成以下结果：

1. 冻结试点范围、Must/Should/Could 约束和 UAT 入口/出口标准。
2. 建立 Resource / Recipe / Demand / Downtime 的最小主数据闭环。
3. 让 Solver 覆盖 UAT Must 级硬约束。
4. 让 Gantt 和版本治理支持业务评审与审批。
5. 完成 UAT 测试、缺陷收口和下一阶段决策。

## 5. 工作包拆解

### WP0：范围、样本与验收冻结

**优先级：P0**

#### 目标

把“下一阶段做什么、不做什么”冻结下来，避免开发期范围漂移。

#### 重点工作

- 确定试点车间/产线、产品族、计划周期。
- 明确目标规模：资源数、工序任务数、停机数、horizon。
- 建立 Must / Should / Could 约束矩阵。
- 明确 UAT 入口/出口标准和缺陷分级规则。
- 明确样本包责任人、冻结日期和审阅节奏。

#### 产出物

- MVP 范围说明
- UAT 场景清单
- 约束优先级矩阵
- UAT 入口/出口标准
- 样本准备责任清单

#### 完成判定

- 产品、业务、研发、算法都能明确回答“本阶段做什么、不做什么”。
- 每个 Must 约束都有来源、校验方式和验收用例。

### WP1：真实样本与字段映射

**优先级：P0**

#### 目标

让样本从“草案”变成可用于导入、求解和 UAT 的标准输入。

#### 重点工作

- 定义 Resource、Recipe、Demand、Downtime 的最小对象。
- 明确数据权威来源：ERP、MES、Excel、主数据系统、人工台账。
- 建立源字段 -> 系统字段映射、类型、必填、校验规则。
- 形成 UAT_v1 样本包和数据质量问题清单。
- 确定是否采用脱敏规则。

#### 产出物

- UAT_v1 样本包
- 字段映射表
- 数据质量问题清单
- 数据脱敏规则

#### 完成判定

- 至少一套真实/脱敏样本可完整映射为排产输入。
- 样本中每个资源、需求、工序、停机都有业务含义。

### WP2：主数据导入与排产场景生成

**优先级：P0**

#### 目标

建立主数据进入系统并生成排产场景的最小产品闭环。

#### 重点工作

- 设计 Resource / Recipe / Demand / Downtime 模板。
- 补齐字段校验、引用校验、时间窗口校验、错误报告。
- 支持导入版本记录：来源、导入人、时间、版本号。
- 根据导入数据生成场景名称、horizon、目标权重、solver config。
- 保留 API 契约，为未来 ERP/MES 对接做准备。

#### 产出物

- 四类导入模板
- 导入 API 契约
- 导入校验规则
- 错误报告格式
- 场景生成说明

#### 完成判定

- UAT_v1 样本可通过导入链路进入系统。
- 非法数据被阻挡在排程主流程之外。
- 同一数据版本可复现同一场景。

### WP3：Solver UAT Must 约束增强

**优先级：P0**

#### 目标

让求解结果满足真实试点必须遵守的硬约束。

#### 重点工作

- 从 Demand + Recipe 展开 Operation。
- 增加工序 precedence。
- 增加基础 changeover / setup 规则。
- 回归验证固定资源、固定开始、停机窗口、交期、优先级。
- 增加不可行/超时/资源不足等失败原因分类。
- 建立真实样本回归用例。

#### 产出物

- Solver MVP 约束说明
- Operation 展开规则
- 求解契约升级说明
- 失败原因分类说明
- 回归样本与测试结果

#### 完成判定

- UAT 样本可成功求解或返回业务可理解的失败原因。
- Must 约束 100% 满足。
- 目标规模下常规场景 5 分钟内返回结果。

### WP4：异步执行稳定性与可观测性

**优先级：P0/P1**

#### 目标

支撑多任务、长耗时和问题定位。

#### 重点工作

- 评估并接入 Redis-backed queue 或等价稳定队列方案。
- 明确状态机：CREATED、QUEUED、RUNNING、SUCCEEDED、FAILED、CANCELLED、TIMEOUT。
- 支持并发限制、超时、取消、重试、阶段进度。
- 增加 jobId、requestId、solver 耗时、失败原因、队列长度等观测字段。

#### 产出物

- 队列/执行架构说明
- 状态机定义
- 监控口径和排障说明
- 错误码/失败分类

#### 完成判定

- 多任务提交后状态不丢失。
- 后端重启、solver 不可达、超时等场景处理策略清晰。
- UAT 期间可通过 jobId 定位问题。

### WP5：Gantt 评审与版本治理产品化

**优先级：P0**

#### 目标

让排程结果可评审、版本可审批、关键操作可追溯。

#### 重点工作

- Gantt 支持按订单/产品/资源/异常任务定位。
- 任务详情展示固定状态、迟交、软约束影响。
- 版本 diff 强化 KPI、资源变化、时间变化、迟交变化。
- 增加审批流、actor attribution、release notes、回退语义。
- 增加基础角色权限：Admin、Planner、Approver、Viewer。

#### 产出物

- Gantt 交互说明
- 审批流程说明
- 版本状态机说明
- 审计字段清单
- 权限矩阵

#### 完成判定

- 业务用户能快速定位一个订单的全部工序安排。
- 一个正式版本具备完整“谁创建、谁审批、谁发布、为什么发布”记录。

### WP6：UAT 与发布收口

**优先级：P0**

#### 目标

把 UAT 变成可执行、可记录、可复盘的正式活动。

#### 重点工作

- 建立 UAT 测试计划、测试用例、测试数据包。
- 覆盖登录权限、导入、排程、Gantt、版本对比、审批、发布、回退、导出。
- 建立缺陷分级、每日 triage、责任人和验证状态。
- 输出操作手册、培训材料、发布检查清单和 UAT 报告。

#### 产出物

- UAT 测试计划与用例
- 缺陷跟踪表
- 回归测试报告
- 用户操作手册
- UAT 验收报告
- 下一阶段 backlog

#### 完成判定

- 核心用例通过率 100%。
- P0 缺陷为 0。
- P1 缺陷有规避方案和修复计划。
- 业务方形成书面结论。

## 8. 里程碑验收口径

| 里程碑 | 验收口径 |
| --- | --- |
| M0 | 范围边界、Must 约束、样本责任和 UAT 标准已确认 |
| M1 | 样本包和字段映射能支撑导入与回归 |
| M2 | 真实数据可进入系统并生成排产场景 |
| M3 | Must 约束在 UAT 样本下稳定通过 |
| M4 | 多任务和失败场景状态可追踪、可恢复 |
| M5 | 业务可评审、审批、发布并理解版本差异 |
| M6 | UAT 通过或形成有条件通过/不通过的明确结论 |

## 9. 当前建议下一步

1. 立刻组织 M0 冻结会，先定试点范围和 Must 约束。
2. 并行启动样本包清理和导入模板设计。
3. 尽早把 Solver 需要的 precedence / setup 用样本驱动明确下来。
4. 在进入 M5 前冻结审批、发布、回退语义和角色边界。
