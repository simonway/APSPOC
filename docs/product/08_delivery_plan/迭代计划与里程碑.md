> 2026-05-12 补记：Snow Beer 后续迭代拆为三个重点阶段。第三期聚焦“主链路排程演示”，第四期聚焦“POC 全业务场景补齐”，第五期聚焦“发布级产品化与正式 release 准备”。只有第五期 release gate 无阻断项后，才将 `pre-release` 推进为第一版正式 `release`。

## 2. 计划假设

- 当前基线能力已稳定：登录、样例排程、通用排程 API、版本/Gantt、导入导出、发布治理 smoke。
- POC 已完成，下一阶段不再以“演示优化”为主要目标，而以“UAT 可用”为主要目标。
- 业务方能提供一个代表性试点范围和一套真实或脱敏真实样本。
- 计划按 1-3 周粒度拆分，允许研发、算法、产品并行推进。
- 复杂高级 APS 能力不作为当前阶段前提。

## 3. 总体目标

在 8-10 周内完成以下结果：

1. 冻结试点范围、Must/Should/Could 约束和 UAT 入口/出口标准。
2. 建立 Resource / Recipe / Demand / Downtime 的最小主数据闭环。
3. 让 Solver 覆盖 UAT Must 级硬约束。
4. 让 Gantt 和版本治理支持业务评审与审批。
5. 完成 UAT 测试、缺陷收口和下一阶段决策。

## 5. 工作包拆解

### WP0：范围、样本与验收冻结

**优先级：P0**

#### 目标

把“下一阶段做什么、不做什么”冻结下来，避免开发期范围漂移。

#### 重点工作

- 确定试点车间/产线、产品族、计划周期。
- 明确目标规模：资源数、工序任务数、停机数、horizon。
- 建立 Must / Should / Could 约束矩阵。
- 明确 UAT 入口/出口标准和缺陷分级规则。
- 明确样本包责任人、冻结日期和审阅节奏。

#### 产出物

- MVP 范围说明
- UAT 场景清单
- 约束优先级矩阵
- UAT 入口/出口标准
- 样本准备责任清单

#### 完成判定

- 产品、业务、研发、算法都能明确回答“本阶段做什么、不做什么”。
- 每个 Must 约束都有来源、校验方式和验收用例。

### WP1：真实样本与字段映射

**优先级：P0**

#### 目标

让样本从“草案”变成可用于导入、求解和 UAT 的标准输入。

#### 重点工作

- 定义 Resource、Recipe、Demand、Downtime 的最小对象。
- 明确数据权威来源：ERP、MES、Excel、主数据系统、人工台账。
- 建立源字段 -> 系统字段映射、类型、必填、校验规则。
- 形成 UAT_v1 样本包和数据质量问题清单。
- 确定是否采用脱敏规则。

#### 产出物

- UAT_v1 样本包
- 字段映射表
- 数据质量问题清单
- 数据脱敏规则

#### 完成判定

- 至少一套真实/脱敏样本可完整映射为排产输入。
- 样本中每个资源、需求、工序、停机都有业务含义。

### WP2：主数据导入与排产场景生成

**优先级：P0**

#### 目标

建立主数据进入系统并生成排产场景的最小产品闭环。

#### 重点工作

- 设计 Resource / Recipe / Demand / Downtime 模板。
- 补齐字段校验、引用校验、时间窗口校验、错误报告。
- 支持导入版本记录：来源、导入人、时间、版本号。
- 根据导入数据生成场景名称、horizon、目标权重、solver config。
- 保留 API 契约，为未来 ERP/MES 对接做准备。

#### 产出物

- 四类导入模板
- 导入 API 契约
- 导入校验规则
- 错误报告格式
- 场景生成说明

#### 完成判定

- UAT_v1 样本可通过导入链路进入系统。
- 非法数据被阻挡在排程主流程之外。
- 同一数据版本可复现同一场景。

### WP3：Solver UAT Must 约束增强

**优先级：P0**

#### 目标

让求解结果满足真实试点必须遵守的硬约束。

#### 重点工作

- 从 Demand + Recipe 展开 Operation。
- 增加工序 precedence。
- 增加基础 changeover / setup 规则。
- 回归验证固定资源、固定开始、停机窗口、交期、优先级。
- 增加不可行/超时/资源不足等失败原因分类。
- 建立真实样本回归用例。

#### 产出物

- Solver MVP 约束说明
- Operation 展开规则
- 求解契约升级说明
- 失败原因分类说明
- 回归样本与测试结果

#### 完成判定

- UAT 样本可成功求解或返回业务可理解的失败原因。
- Must 约束 100% 满足。
- 目标规模下常规场景 5 分钟内返回结果。

### WP4：异步执行稳定性与可观测性

**优先级：P0/P1**

#### 目标

支撑多任务、长耗时和问题定位。

#### 重点工作

- 评估并接入 Redis-backed queue 或等价稳定队列方案。
- 明确状态机：CREATED、QUEUED、RUNNING、SUCCEEDED、FAILED、CANCELLED、TIMEOUT。
- 支持并发限制、超时、取消、重试、阶段进度。
- 增加 jobId、requestId、solver 耗时、失败原因、队列长度等观测字段。

#### 产出物

- 队列/执行架构说明
- 状态机定义
- 监控口径和排障说明
- 错误码/失败分类

#### 完成判定

- 多任务提交后状态不丢失。
- 后端重启、solver 不可达、超时等场景处理策略清晰。
- UAT 期间可通过 jobId 定位问题。

### WP5：Gantt 评审与版本治理产品化

**优先级：P0**

#### 目标

让排程结果可评审、版本可审批、关键操作可追溯。

#### 重点工作

- Gantt 支持按订单/产品/资源/异常任务定位。
- 任务详情展示固定状态、迟交、软约束影响。
- 版本 diff 强化 KPI、资源变化、时间变化、迟交变化。
- 增加审批流、actor attribution、release notes、回退语义。
- 增加基础角色权限：Admin、Planner、Approver、Viewer。

#### 产出物

- Gantt 交互说明
- 审批流程说明
- 版本状态机说明
- 审计字段清单
- 权限矩阵

#### 完成判定

- 业务用户能快速定位一个订单的全部工序安排。
- 一个正式版本具备完整“谁创建、谁审批、谁发布、为什么发布”记录。

### WP6：UAT 与发布收口

**优先级：P0**

#### 目标

把 UAT 变成可执行、可记录、可复盘的正式活动。

#### 重点工作

- 建立 UAT 测试计划、测试用例、测试数据包。
- 覆盖登录权限、导入、排程、Gantt、版本对比、审批、发布、回退、导出。
- 建立缺陷分级、每日 triage、责任人和验证状态。
- 输出操作手册、培训材料、发布检查清单和 UAT 报告。

#### 产出物

- UAT 测试计划与用例
- 缺陷跟踪表
- 回归测试报告
- 用户操作手册
- UAT 验收报告
- 下一阶段 backlog

#### 完成判定

- 核心用例通过率 100%。
- P0 缺陷为 0。
- P1 缺陷有规避方案和修复计划。
- 业务方形成书面结论。

## 6. Snow Beer 三/四/五期交付边界

### 6.1 第三期：Snow Beer 主链路排程演示版

**阶段目标**：第三期结束后，客户至少可以看到 Snow Beer 从需求到包装的主业务链路排程演示。重点是主链路可跑通和可解释，不把复杂行业规则、性能优化、正式审批治理和 UI 精修作为阻断项。

| 工作包 | 重点内容 | 完成判定 |
| --- | --- | --- |
| P3-WP1 主链路范围冻结 | 冻结需求、库存、包材、糖化、发酵、过滤、包装、插单和基础不可行解释的演示路径 | 主链路场景清单经产品/业务确认 |
| P3-WP2 主链路样本包 | 扩展需求、库存、包材、糖化、发酵、过滤、包装、插单样本 | 主链路每个环节有可运行样本 |
| P3-WP3 场景生成 | 从需求和主数据生成离散化排程任务，保留需求追溯 | 场景可提交 solver |
| P3-WP4 Solver 主链路能力 | 支持糖化、发酵、过滤、包装的离散化任务排程 | 主链路有演示结果或业务化失败原因 |
| P3-WP5 基础不可行解释 | 对产能不足、物料不足、窗口冲突、无资源等失败分类 | 客户可理解失败原因 |
| P3-WP6 主链路演示脚本 | 固化导入、排程、Gantt、方案对比和结果解释路径 | 产品/售前可按脚本独立演示主链路 |

#### 6.1.1 第三期第一轮开发状态（2026-05-12）

- `P3-WP2 / P3-WP3 / P3-WP4` 已完成第一轮可运行闭环：新增 `docs/sample-packages/snow_beer_main_chain_phase3/`，覆盖需求、库存、包材、糖化、发酵、过滤、包装、插单、停机和包装换型。
- 样本生成结果：3 条需求、4 个请求 lot、1 个 finished-goods 库存覆盖 lot、3 个 planned lot、12 个离散任务、9 条 precedence、0 个 bridge adjustment。
- 自动化验证：`mvn -f backend/pom.xml test` 通过 45 个 backend 测试；`PYTHONPATH=solver python3 -m unittest discover -s solver/tests` 通过 13 个 solver 测试。
- 集成验证：`scripts/uat_package_smoke.py docs/sample-packages/snow_beer_main_chain_phase3` 已跑通导入批次、场景生成、排程提交和 Gantt 数据，job 为 `SUCCEEDED`，solverStatus 为 `OPTIMAL`，Gantt bars 为 12。
- `P3-WP6` 已在 `docs/sample-packages/snow_beer_main_chain_phase3/00_readme.md` 沉淀第一版演示脚本，下一步重点是 `P3-WP1` 的业务范围确认和脚本走查确认；第四期复杂行业规则和第五期 release gate 不因本轮闭环而提前纳入第三期阻断项。

### 6.2 第四期：Snow Beer 全业务场景补齐版

**阶段目标**：第四期结束后，Snow Beer POC 全业务场景均具备演示、排程或业务化失败解释能力。重点是复杂业务场景补齐，不承担正式 release 门禁。

| 工作包 | 重点内容 | 完成判定 |
| --- | --- | --- |
| P4-WP1 复杂场景范围冻结 | 冻结成熟窗口、罐体、清酒罐、多锅次、物料可用时间等场景口径 | 全场景清单经产品/业务确认 |
| P4-WP2 复杂样本包 | 扩展发酵罐、成熟窗口、过滤到清酒、清酒罐中转、静置/保鲜样本 | 每个复杂场景有可运行样本 |
| P4-WP3 行业规则建模 | 支持或近似支持发酵成熟、罐体占用、不可混装、清酒罐中转等关键约束 | 每类规则有演示结果或边界说明 |
| P4-WP4 全场景回归 | 将主链路和复杂场景纳入全场景回归 | 全场景可重复运行 |
| P4-WP5 近似边界说明 | 对连续流、浓度/收率、采购反推等能力明确后置或近似口径 | 客户演示不误承诺 |

### 6.3 第五期：发布级产品化与正式 Release 准备版

**阶段目标**：第五期结束后，基本具备把 `pre-release` 推进为第一版正式 `release` 的条件。重点是发布级质量，而不是继续扩大 Snow Beer 业务范围。

| 工作包 | 重点内容 | 完成判定 |
| --- | --- | --- |
| P5-WP1 性能优化 | Snow Beer 全场景样本求解、导入、Gantt 渲染性能基线 | 性能回归达标 |
| P5-WP2 执行稳定性 | 队列化、超时、取消/重试、完整状态机、可观测性 | 多任务和失败场景稳定可追踪 |
| P5-WP3 审批与治理 | 角色权限、审批/驳回、发布、回退、actor attribution、审计 | 正式版本可完整追溯 |
| P5-WP4 UI/交互优化 | 场景入口、缺料/延期/换型/冲突高亮、方案对比、错误可读性 | UI 走查和客户演示通过 |
| P5-WP5 Release 门禁 | 全场景 smoke、操作手册、发布说明、release checklist、回退方案 | 无 release 阻断项 |
