> 本文档用于把 Snow Beer 第三期从“第一轮技术闭环已完成”推进到“范围、演示、回归和验收口径全部收口”的可执行计划。

## 2. 背景与目的

截至 `2026-05-13`，第三期已经完成第一轮技术闭环：

- 已新增 `docs/sample-packages/snow_beer_main_chain_phase3/` 主链路样本包。
- 已形成 `需求 -> 场景生成 -> solver -> Gantt` 的可运行链路。
- 已有 backend / solver 回归，以及样本包单独 smoke 验证。

但当前仍不能直接把第三期判定为“已正式完成”，原因在于：

- 主链路业务范围仍未正式冻结。
- 演示脚本已有初稿，但还未完成产品/售前走查。
- 基础不可行解释仍偏技术验证口径，尚未完全沉淀为业务可理解话术。
- `snow_beer_main_chain_phase3` 已切入默认发布回归主路径，样本也已纳入版本控制暂存区，但样本级等价回归和最终提交留痕仍需继续收口。
- 样本、测试、文档和验收结论之间仍存在少量收口动作。

本计划的目标是把第三期剩余动作明确到可执行、可验收、可留痕的程度。

1. 冻结范围。
2. 走查演示。
3. 补齐失败解释。
4. 固化回归资产。

## 4. 收口目标

第三期收口完成时，应同时满足以下条件：

1. 团队内外对第三期“做什么、不做什么”只有一套口径，不再混入第四期/第五期内容。
2. 产品、售前可以不依赖研发口头补充，按统一脚本独立演示主链路。
3. 主链路失败场景能够用业务可理解语言解释，而不只暴露底层 `INFEASIBLE`。
4. `snow_beer_main_chain_phase3` 成为正式受控的样本和回归资产，而不只是本地验证材料。

## 6. 建议执行顺序

建议按以下顺序推进：

1. `WP-A` 主链路范围冻结
2. `WP-B` 主链路演示脚本走查
3. `WP-D` 样本与回归资产固化
4. `WP-E` 默认回归与测试补强
5. `WP-C` 基础不可行解释收口
6. `WP-F` 收口评审与结论留痕

排序原则如下：

- 范围不冻结，演示和验收都会反复变化。
- 演示脚本不走查，第三期即使技术可跑通，也无法稳定对外表达。
- 样本不纳管、默认回归不补齐，第三期结论容易被后续改动悄悄破坏。
- 不可行解释要在演示口径和回归基线稳定后再统一收口，避免反复改话术。

## 8. 不纳入第三期收口的内容

以下内容仍按既有边界留在第四期或第五期，不作为第三期收口阻断项：

- 发酵成熟窗口
- 清酒罐中转、静置/保鲜窗口
- 罐体容量、占用、不可混装、多锅次满罐
- 连续流、浓度/收率、采购反推
- 发布级性能优化
- 正式审批治理补强
- UI 视觉和交互 polish

## 9. 第三期退出标准

只有同时满足以下条件，才建议对内声明“第三期正式完成”：

1. `SB-P3-AC-01` ~ `SB-P3-AC-08` 均有明确结论。
2. `snow_beer_main_chain_phase3` 已成为正式纳管样本。
3. 产品/售前已按正式脚本完成一轮走查。
4. 第三期失败口径已有书面解释。
5. 第四期后续输入问题已被记录，不再混入第三期完成定义。
