# 版本发布治理清单

## 1. 目标

本清单用于把当前 `dev` 分支上的 APS POC 版本，整理成一个可回溯、可验证、可回退的发布版本。

当前 `v0.2.0` 发布状态与分支职责，见：

- [2026-05-11_v0.2.0_pre-release_状态说明.md](/Users/simon/Documents/MyProgramming/APSPOC/docs/release/2026-05-11_v0.2.0_pre-release_状态说明.md:1)

当前推荐对外口径：

> 二期路线图闭环完成，系统可进入业务演示、UAT 与发布验收。

如果本次发布仍基于当前代码状态，发布说明中不应误承诺以下超出当前验证边界的能力：

- Redis-backed 分布式队列或多节点执行编排已经接入正式主链路
- 更长求解预算一定会稳定带来更优 KPI，或当前 solver 已完成所有规模场景下的性能承诺

## 2. 推荐 Git 流程

1. 从 `dev` 创建发布分支，例如 `release/v0.1.0`
2. 在发布分支执行 `./scripts/verify-release.sh`
3. 只修复阻断发布的问题，不在发布分支继续叠加新需求
4. 更新根目录 `CHANGELOG.md`
5. 在发布分支打标签，例如 `v0.1.0`
6. 合并 `release/v0.1.0` 到 `master`
7. 再把 `master` 或发布修复结果回合并到 `dev`

## 3. 发布前检查

- `git status` 中没有误提交的本地临时文件
- 已确认 `auto_switch_proxy.py` 不属于 APS 项目提交范围；若该文件仅为本地旁支脚本，可使用 `git update-index --skip-worktree auto_switch_proxy.py` 避免干扰发布整理
- `./scripts/verify-release.sh` 全部通过
- `CHANGELOG.md` 已更新到本次发布版本
- README、运行手册、验收记录已同步
- 已确认对外发布说明使用“路线图闭环完成，可进入业务演示/UAT/发布验收”的统一口径
- 已确认当前数据库中的测试版本和审计数据是否需要清理
  参考：[2026-05-11_发布前测试数据清理清单.md](/Users/simon/Documents/MyProgramming/APSPOC/docs/release/2026-05-11_发布前测试数据清理清单.md:1)
- 已人工补验 Gantt 拖拽时间悬浮卡片可见，且不会被任务条遮挡
- 已使用当前 backend 进程重新生成业务样本版本，不复用旧版本快照
- 已确认业务样本同时满足：
  - 库存覆盖订单可在 Gantt 中被看见
  - 临期需求不会被大面积提前到周期最前面
- 已确认样包导入对常见中文编码文件可用，不要求业务先手工转码

## 4. 应用内版本治理检查

- 至少生成一个新的 `DRAFT` 版本
- 已填写 `Release Note`
- 已填写治理备注并执行 `Ready for Release`
- 已使用 `Admin / Approver` 角色执行 `Approve`
- 已执行 `Publish`
- 已检查 `Version Governance Audit` 和版本历史
- 已检查版本 diff 中 `新增 / 调整 / 移除` 变更项点击后，存在明显高亮或状态反馈
- 如需验证回退，已选取一个 `ARCHIVED` 或 `ROLLED_BACK` 版本执行 `Rollback`

说明：

- 审批流和角色权限已落地，不再需要把版本治理表述为单用户 MVP
- 如果某个演示环境没有预置 `planner / approver / viewer` 账号，应单独说明是环境准备问题，不是产品能力缺口

## 5. 发布后动作

- 记录发布 tag、发布时间、责任人
- 记录 GitHub Release 当前是 `pre-release` 还是正式版，并与实际对外口径保持一致
- 记录本次发布对应的演示版本或数据库快照
- 如发现问题，优先通过应用内 `Rollback` 恢复生效版本
- 如问题来自代码，回到 `dev` 或新的修复分支处理，再重新走发布流程

## 6. 回退原则

- 应用内回退：优先使用版本治理中的 `Rollback`
- 代码回退：通过新的修复提交或回退提交处理，不要在共享分支直接做不可追溯修改
- 数据回退：如需恢复数据库，先确认是否保留审计历史，再执行快照恢复
