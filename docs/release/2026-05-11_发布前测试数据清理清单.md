## 1. 清理原则

- 如果目标是“生成一份可追溯的发布验收证据”，优先保留 smoke 产物，并在发布说明中标记这些版本/作业来自 `2026-05-11` 验收。
- 如果目标是“交付一个干净的演示数据库”，优先使用验收前快照恢复或重建环境，不建议手工逐表清理。
- 当前应用内可直接清理的是 `DRAFT` 版本。
- 当前应用内没有对等的 `job / import batch / audit event` 删除入口，这类数据更适合通过数据库快照恢复或环境重建处理。
- 根目录下的 `auto_switch_proxy.py` 属于本地旁支脚本，不属于 APS 项目的发布材料或测试数据清理范围。

## 3. 推荐处理方式

### 3.1 应用内可直接清理

- 删除 smoke 产生的 `DRAFT` 版本：
  - 前端版本列表中支持勾选并批量删除草稿
  - 对应后端接口：
    - `DELETE /api/v1/versions/{versionId}`
    - `POST /api/v1/versions/delete-drafts`
- 建议优先删除“纯验证用途、未参与发布说明”的草稿版本，例如：
  - 物料流可行版本
  - UAT 样包 smoke 生成的临时草稿版本

### 3.2 建议保留到签收完成后再处理

- 参与了 `Ready for Release -> Reject -> Approve -> Publish -> Rollback` 链路的治理验证版本
- 对应的版本 history 和 audit history
- `release-smoke-summary.json` 与 `uat-package-smoke-summary.json`

原因：

- 这些数据本身就是发布验收证据
- 如果先删再补文档，后续很难解释“验收到底在什么版本上完成”

### 3.3 更适合通过环境重建处理

- `job-*` 排程作业记录
- `imp-*` 导入批次
- `smoke_material_*` / `uat_v1_2026_04_28_smoke_*` 对应的持久化导入数据
- 为 smoke 生成的审计事件和非草稿治理痕迹

原因：

- 当前产品能力没有成体系的应用内删除入口
- 手工逐项清理容易破坏版本历史与审计链条

## 4. 发布前最小动作建议

如果当前环境要继续作为“发布演示环境”，建议至少做到：

1. 保留 `.runtime` 中的两个 smoke summary 文件。
2. 在验收记录或发布说明里注明 `2026-05-11` smoke 产生的关键版本 ID。
3. 删除不需要展示给业务的临时 `DRAFT` 版本。
4. 确认最终对外展示的 `RELEASED` 版本不是 smoke 临时版本，而是重新生成或明确指定的业务样本版本。

如果当前环境要变成“干净交付环境”，建议：

1. 先保存 `CHANGELOG`、验收记录和 `.runtime` summary 作为证据。
2. 回滚到验收前数据库快照，或重建数据库后重新导入目标业务样本。
3. 使用新环境重新生成最终演示版本，不复用 `2026-05-11` smoke 产生的临时版本。
